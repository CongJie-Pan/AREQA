## 二、關於「LLM 對話鷹架」——先問自己這幾個問題

1. **你要動的是「模型本身」還是「外層系統」？**
   微調模型（Fine-tuning）需要訓練資料、算力、且改變的是模型底層行為；而 Prompt Engineering／System Prompt 只是在對話開始前給模型一套規則。**以你現在的資源（沒有龐大算力、沒有自有訓練資料集），哪一種才是你實際做得到的？**

2. **這個鷹架是「固定劇本」還是「動態判斷」？**
   如果是固定劇本，你可以用 System Prompt 寫死規則（例如：「每次回答前，先列出至少兩種對立觀點，再反問使用者的立場」）。如果是動態判斷，你需要系統即時偵測使用者的行為（例如：偵測到使用者只是複製貼上），才觸發鷹架介入——這就像你讀過的那篇《Mitigating cognitive offloading》,它有一個會自動偵測「認知卸載風險」並跳出提示的系統架構。**你的研究問題裡講的「對話鷹架」，是想做前者的「靠 Prompt 設計出來的固定策略」，還是後者的「靠系統偵測行為觸發的動態機制」？**

3. **AREQA 現在的技術水位在哪裡？**
   你已經開發的 AREQA，它現在的對話邏輯，比較接近哪一種？如果你的研究問題要準確描述「載體」，其實應該直接對應你系統實際能做到的技術層級,而不是先寫一個理想化的描述,之後才發現系統做不到。

**引導方向：** 你可以把這個詞拆成「機制（不確定性揭露/多視角/後設認知提問）」+「實作方式（Prompt 設計 vs 行為偵測觸發）」兩層來寫,這樣審查的人才知道你到底要不要開發一個「能偵測使用者行為」的系統,還是只是設計一套「固定對話腳本」。
