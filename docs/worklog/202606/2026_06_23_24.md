## ⚖️ 實作策略抉擇：獨立 MVP vs. 直接實作
根據我們專案的開發規範（嚴格禁止重複的架構實作與複製程式碼，以防堵技術債），我強烈建議「直接實作至主系統（透過延伸現有檔案）」。

### 為什麼不建議做獨立 MVP？

1. 代碼重複率高：如果做一個獨立的 EDF 系統，您必須重新寫一遍 LLM 串接、對話狀態管理與記憶庫初始化，這會產生大量臨時程式碼。
2. 整併痛苦：當您要把獨立 MVP 合併回主系統時，會遇到異步串流（FastAPI StreamingResponse）、GUM 資料庫鎖定等問題，反而需要重構兩次。

### 為什麼「直接實作」最安全、最快？

因為您這一週完成的 Hot/Cold Memory 分層與 Compaction 機制，已經幫 Evidence 模組 打下了完美的物理地基！我們只需要在現有的  main.py  與  gum_integration.py  加上幾個「邏輯插槽
(Middleware/Slots)」，就能優雅地嵌入 EDF 與 ComPeer。

## 🗺️ EDF + ComPeer 嵌入主系統的具體實作藍圖

我們可以用一個非常乾淨的方式，將這兩篇論文的靈魂實作到現有的後端架構中：

### 1. Decision & Feedback 模組（EDF 決策嵌入）

在  backend/main.py  接收到使用者訊息，準備生成回答前（大約在系統提示詞注入的階段）：

• 作法（快思考）：
我們先讓一個輕量級的 LLM（或用 Prompts 控制）先執行 Dialogue Policy 分類。
    1. 它會去讀取您的  MemoryStore  (Hot) 看看學生之前的掌握度。
    2. 判定這回合該採用的 Policy： PROBE_UNDERSTANDING （探查理解）、 SUGGEST_ACTION （引導解題）、還是  PUSH_LIMIT （挑戰）。
    3. 將決定好的 Policy（例如： [POLICY: SUGGEST_ACTION] ）與提示詞模板，直接動態注入到  SYSTEM_PROMPT  中，再讓主模型進行串流生成（Feedback）。
• 這就完成了 EDF 的決策與回饋閉環。

### 2. Proactive Scheduler（ComPeer 主動關懷嵌入）

在  backend/main.py  的對話處理中：

• 作法（事件偵測與計時）：
    1. 當使用者發送訊息或對話結束後，後端啟動一個非同步任務（ asyncio.create_task ）。
    2. 如果偵測到學生「連續錯題」或「在編輯器卡關超過 3 分鐘」（這是我們的 Event Detector）。
    3. 系統會排程（Schedule）一個 proactive event。
    4. 當排程觸發時，後端不主動發送文字（因為這是網頁版），而是透過 FastAPI SSE (Server-Sent Events) 管道，推送一個名為  proactive_hint  的事件到前端。
    5. 前端收到事件後，在網頁聊天室的角落顯示一個溫柔的 Preview 元件（例如小燈泡：「💡 發現你卡在 Recursion 一陣子了，需要小提示嗎？」）。
