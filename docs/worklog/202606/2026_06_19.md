上一個agy 的詢問prompt為 :

"""
我正在開發一個基於 LLM 的 AI 聊天系統（後端使用 Python/FastAPI），目前我們實作了一個「長效記憶（Long-term Memory）」模組，但遇到了一些瓶頸。請根據目前業界的最佳實踐與開源趨勢幫我進行架構優化。

    【目前的記憶架構與機制】
    1. 非同步萃取：背景任務會分析對話，將用戶事實與偏好萃取為「命題 (Propositions)」。
    2. 存儲與索引：命題存放在 SQLite，並使用 FTS5 (porter ascii tokenizer) 建立全文檢索。
    3. 兩階段檢索：
       - 第一階段 (Sparse)：用 `jieba` 對用戶問題進行斷詞，透過 SQLite FTS5 MATCH (BM25) 撈出關鍵字匹配的候選記憶。
       - 第二階段 (Semantic/Logic)：呼叫小型 LLM 判斷問題意圖，與候選記憶的標籤進行比對過濾 (Label Density Ranking)。
    4. 注入：將過濾後的記憶作為 Context 注入給主模型。

    【目前的痛點】
    1. 中文斷詞與 FTS 的相容性災難：SQLite 的 porter 分詞器無法正確切分無空白的中文，導致整句中文變成一個巨大 Token。BM25 關鍵字搜尋時常回傳 0 筆結果，直接導致後續優秀的 AI 過濾機制失效。
    2. 純關鍵字搜尋的侷限：即使修復了中文斷詞，純 BM25 仍缺乏「語意理解」，無法應對同義詞或隱含意圖的提問。

    【我的需求】
    請基於目前的業界最佳實踐（例如 Mem0, Zep, MemGPT/Letta, GraphRAG 等專案的思路），為我規劃一個「更好、更現代化的 AI 繁體中文長效記憶提取架構」。請具體回答以下問題：

    1. 核心替換方案：我該如何取代現有的 SQLite FTS5 第一階段檢索？（推薦向量檢索 Dense、混合檢索 Hybrid 還是 Knowledge Graph？）
    2. 中文語境優化：針對繁體中文，推薦的 Embedding 模型或檢索策略是什麼？
    3. 架構設計：如果採用混合檢索 (Hybrid Search)，有什麼輕量級、適合 Python 後端的開源資料庫或工具庫（例如 Qdrant, Milvus Lite, Chroma）推薦？
    4. 業界趨勢對比：與 MemGPT 這種「讓 LLM 主動調用工具去搜尋記憶」的 OS-like Memory 模式相比，被動的兩階段檢索（我們現在的做法）在優劣勢上有何差異？我該轉換思路嗎？

    請提供有具體技術選型的架構藍圖，並以專業、條理清晰的繁體中文回答。
"""

當解法三實作ok後，在依照以下問題順道測試解法二的內容 :

  #### 情境一：建立帶有 STITCH 標籤的記憶

  • 您可以輸入： 我覺得林黛玉的性格很多愁善感，特別是她在看到落花時寫下《葬花吟》的那一幕，讓我印象非常深刻。 
  • 預期行為：這句話寫入資料庫時，LLM 會自動為這段記憶打上 STITCH 標籤（例如  context_scope="人物分析" ,  target="林黛玉" ,  event_types=["讀後感"]  等）。

  #### 情境二：觸發 STITCH 意圖預測與精準過濾（Cache Miss）

  • 您可以輸入： 你記得我之前對林黛玉有什麼看法嗎？ 
  • 預期 Terminal Log：
    INFO: [STITCH] Intent Cache Miss. Querying LLM for intent prediction...                                                                                                                                  
    INFO: [STITCH] Predicted Labels: {"selected_targets": ["林黛玉"], "selected_context_scopes": ["人物分析"], ...}
    INFO: [STITCH] Filtering X candidates using Label Density Ranking...
    INFO: [STITCH] Filtered down to Y candidates.

  • 說明：這是第一次問這個問題，系統會分析出你想問的是「林黛玉」，並精準地把剛才那段記憶拉出來回答你。

  #### 情境三：觸發 LRU Cache（Cache Hit，節省資源）

  • 您可以輸入： 你記得我之前對林黛玉有什麼看法嗎？ （輸入完全相同的字）
  • 預期 Terminal Log：
    INFO: [STITCH] Intent Cache Hit. Using cached labels for query: '你記得我之前對林黛玉有什麼看法嗎？'
    INFO: [STITCH] Filtering X candidates using Label Density Ranking...

  • 說明：系統認得這是剛剛查過的問題，直接從快取（Cache）拿出「林黛玉」這個標籤去搜尋，不會再花費 LLM API 的費用去判斷意圖。

  #### 情境四：觸發 STITCH 嚴格模式（精準攔截幻覺）

  • 您可以輸入： 那我們有討論過薛寶釵的《冷香丸》配方嗎？ 
  • 預期 Terminal Log：
    INFO: [STITCH] Intent Cache Miss. Querying LLM for intent prediction...
    INFO: [STITCH] Predicted Labels: {"selected_targets": ["薛寶釵", "冷香丸"], ...}
    WARNING: [STITCH] Strict mode: No candidates matched the predicted labels. Returning empty results.

  • 說明：LLM 知道你在問「薛寶釵」，但系統在資料庫裡只找得到「林黛玉」的標籤，兩者對不上，因此回傳空結果。AI 就會據實以告：「我們之前沒有討論過薛寶釵喔。」而不會被傳統關鍵字搜尋（BM25）的雜訊誤導而亂回答。

  #### 情境五：觸發 Fallback（退回傳統檢索）

  • 您可以輸入： 你覺得今天會下雨嗎？ 
  • 預期 Terminal Log：
    INFO: [STITCH] Predicted Labels: {"selected_targets": [], "selected_context_scopes": [], ...}
    INFO: [STITCH] No labels selected by LLM. Fallback to pure BM25 search.

  • 說明：這句話跟《紅樓夢》無關，LLM 預測不出任何大觀園的標籤（皆為空），系統就會聰明地啟動防呆機制，退回到傳統的全文搜尋模式。
