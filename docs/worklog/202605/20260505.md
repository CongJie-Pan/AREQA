## 1. 建立基準點 (Establishing the Baseline)

### 偵錯與分析報告
針對用戶報告的「SSE 串流故障」與「建議問題 (Suggestion Questions) 消失」問題，通過對比 `38ac7b25fec6d17fd75a421a851b3eb44b0eff1b` (已知正常版本) 與目前代碼的差異，鎖定了功能失效的具體位置與原因。

#### A. 失效發生的時間點
問題主要源於 2026年5月3日的兩次重構 Commit：
1. **Commit `088d91b` (08:33):** 試圖優化建議問題與 SSE 解析。
2. **Commit `fba56ea` (09:32):** 進行前端 StreamManager 模組化與快照模式重構。

#### B. 核心故障原因 (Root Causes)
1. **SSE 緩衝阻塞 (Buffering Issue):**
   - **變動：** 在 `backend/main.py` 的重構中，`StreamingResponse` 的 `headers` 被意外移除。
   - **影響：** 缺少 `X-Accel-Buffering: no` 導致 Nginx/瀏覽器快取串流內容，造成文字無法即時輸出或顯示空白。
2. **訊息分頁邏輯錯誤 (Logic Regression):**
   - **變動：** 錯誤地將 `last_user_msg` 的檢索範圍限制在 `messages[offset : offset + limit]` (前20條)。
   - **影響：** 在長對話中，系統無法找到當前用戶問題，導致 RAG 檢索與建議問題生成邏輯因缺少 Query 而失效。
3. **狀態定義不一致 (Enum Mismatch):**
   - **變動：** 後端引入了新的 `refused` 狀態，但前端 TypeScript 定義與 `RAGStatusPanel` 未同步更新。
   - **影響：** 當觸發領域防護 (Gatekeeper) 時，前端無法解析狀態，導致 UI 鎖死在加載動畫。

#### C. 已採取的修復措施
- **後端：** 恢復 `StreamingResponse` 關鍵標頭；將訊息檢索改回 `reversed(chat_req.messages)` 全域搜索。
- **前端：** 同步 `refused` 狀態定義至 `types.ts` 與 `RAGStatusPanel`；強化 `StreamManager` 對建議問題的捕獲邏輯。

### 為什麼測試全過但功能壞了？
- **原因：** 現有的整合測試僅檢查了 HTTP 狀態碼 (200 OK)，未深入檢查 SSE 串流內部的事件完整性。

## 5. 開發的檢討

根據"docs/miscellaneous/google_engineer_fixBug_method.md" 的覆盤，下次的開發流程需要注意以下 : 

根據 docs/miscellaneous/google_engineer_fixBug_method.md 的覆盤，未來的開發流程必須嚴格遵守以下準則，以防止類似的 Regression 再次發生：

1. 「止血」優先於「美化」 (Fix First, Refactor Later)：
    * 在修復 Bug 時，嚴禁同時進行大規模的代碼重構或模組化。
    * 修復必須是原子性 (Atomic) 的，確認功能恢復並通過測試後，再考慮優化結構。
2. 串流協議的「敏感性」意識：
    * SSE 等串流協議極度依賴特定 Headers（如 X-Accel-Buffering）與訊息順序。
    * 任何涉及 API 介面定義（如新增分頁參數）的改動，必須評估對串流上下文的影響。
3. 建立「事件級」測試 (Fine-grained Testing)：
    * 不能只滿足於 HTTP 200。未來的集成測試必須模擬 SSE 讀取，校驗 event: done 或 suggestions 等自定義事件是否確實發送。
4. 拒絕「順便」心態：
    * 模組化過程中「順便」改動的每一行程式碼，都有可能成為破壞穩定系統的黑天鵝。
