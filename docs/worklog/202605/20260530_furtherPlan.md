# 未來系統改善規劃：GUMs 狀態管理與 RAG 檢索降噪

## 這是要解決什麼問題 ?

1. **單次問答模式無法「因材施教」**：傳統的 RAG 系統與問答機器人缺乏對使用者長期弱點與特性的認知，無法根據不同學生的國文程度（如：文言文底子弱）自動給予客製化的註釋與解析。
2. **高密度文言文導致的「注意力失焦 (Lost in the Middle)」與檢索雜訊**：面對《紅樓夢》等高密度的古典文學，語言模型若被塞入過多或不精準的 RAG 參考文獻，極易產生「檢索後扭曲」與事實性幻覺，且RAG針對同一個問題每次的檢索文獻都不一樣、不穩定。
3. **模型微調的高成本與不可控性**：先前的實驗證明，純模型加上優化過的 RAG 管線，在事實準確性上的表現已經非常優異且穩定。因此，我們希望跳脫「必須不斷微調 (Fine-tuning) 基礎模型」的思維，轉而用純推論（Inference-only）的工程手段與提示詞工程來解決上述問題。

## 研究方法

本計畫將不涉及模型的重新訓練與微調，而是專注於系統層面的**架構設計（Architecture Design）**與 **RAG 管線工程優化（Pipeline Optimization）**。

*   **領域專屬使用者模型 (Domain-Specific GUM) 的狀態管理**：
    引入「使用者輪廓狀態機（User Profile State Management）」。透過輕量級資料庫（如後端 JSON 檔案或 SQLite）記錄每位學生的「互動歷史」與「弱點標籤」。在每次呼叫線上 LLM API 前，系統會動態攔截並提取該使用者的專屬標籤，將其無縫注入（Inject）至 API 的 System Prompt 中。此方法完全依賴系統狀態追蹤與 Prompt Engineering 來引導線上 API 的生成行為，達成因材施教。

*   **檢索降噪與動態上下文壓縮 (Context Compression)**：
    1.  **動態重排閾值 (Dynamic Reranker Threshold)**：利用現成的 Embedding API 或輕量級 Cross-Encoder 模型計算相似度分數，並寫入 if-else 邏輯閘，將低於閾值的雜訊文獻直接過濾剔除。
    2.  **LLM 輔助的降維壓縮 (LLM-based Context Summarization)**：在將檢索到的多篇古文丟給最終負責回答問題的 API 之前，先額外呼叫一次線上 API，讓模型對這些冗長的文獻進行「精簡摘要」，將原本鬆散的段落濃縮為高密度的知識文本，從而減輕主回答模型的上下文認知負擔。

## 實踐計畫

以下為具體的工程開發階段：

### 第一階段：Domain-Specific GUM 狀態管理與提示詞注入
1.  **API Schema 更新**：修改後端 `backend/main.py` 中的 `ChatRequest` 結構，增加 `user_id` 欄位以識別使用者。
2.  **輕量資料庫建置**：建立一個簡易的 Mock DB，儲存特定 `user_id` 的「弱點標籤」（例如：`"文言文底子弱"` 或 `"喜歡深度的文學隱喻"`）。
3.  **Prompt 攔截與注入實作**：在後端呼叫主要生成 API 之前，讀取對應的弱點標籤，並動態組裝至 `SYSTEM_PROMPT` 中（例如：「System: 這個學生文言文底子弱，請在回答時自動加上字詞解釋」）。
4.  **驗證階段**：透過 Swagger UI 傳送帶有不同 `user_id` 的請求，檢驗線上 API 是否能根據動態注入的弱點標籤，給出風格不同但事實一致的解說。

### 第二階段：RAG 檢索降噪與上下文壓縮管線優化
1.  **強化動態重排閾值**：重構 `src/main/python/services/rag_service.py` 內的過濾邏輯，根據 Reranker 分數設置更嚴格的截斷門檻，確保只有高置信度的文獻能進入下一關。
2.  **實作上下文壓縮模組**：
    *   撰寫一個新函數 `_compress_context_with_llm()`，呼叫指定的線上 API 進行文獻摘要。
    *   設計壓縮專用的 System Prompt：「請根據使用者的問題，將以下檢索到的古文片段提取出核心事實與定義，去除無關雜訊並濃縮在 300 字內。」
3.  **管線整合**：將此壓縮模組安插至檢索完成與生成答案之間的流程，並處理 SSE 串流狀態（例如傳送 "✂️ 濃縮精簡檢索內容..." 以優化使用者等待的體驗）。
4.  **驗證階段**：針對複雜題型進行測試，確認額外的上下文壓縮呼叫是否有效減少了主回答階段的幻覺現象，並評估回答準確性與二次 API 呼叫帶來的延遲（Latency）平衡。
