# AREQA 人工測試劇本：記憶治理、回覆脈絡與 ComPeer

本劇本依據 `memory_managing_principle.md` 與 2026/07/16 改善計畫，驗證「畫面沒有顯示錯誤記憶」以外的實際安全性：系統只能保存可追溯的使用者證據、候選記憶必須遵守生命週期與晉升門檻，且 ComPeer 在正常與 Redis 暫時失敗時都有可追蹤的遞送結果。

## 測試前置條件

- 使用全新的測試帳號，該帳號沒有既有 verified profile、cold candidate、hot memory 與未讀信件。
- 準備至少六個新的對話，分別記錄其 `conversation_id`；同一幕若要求不同對話，不能重用 conversation ID。
- 將 `memory_candidate_auto_promote_conversations` 設為 `2`。若正式環境使用較高數值，需建立相同數量的獨立對話；不得將數值設為低於 `2`。
- 工程人員可查詢此帳號的 cold candidate、verified profile、記憶操作紀錄、結構化日誌、`mailbox_delayed_tasks` 與信箱資料；可取得 `message_id`、`conversation_id` 和 `task_id`。
- 第十幕需有信箱資料庫，並可在 delayed-mail enqueue 階段暫時模擬 Redis timeout 後恢復 Redis。

## 第一幕：初次學習問題與敏感內容不得成為長期記憶

### 輸入

在「對話 A」輸入：

```text
我下週要考高一物理了，但我之前連國中理化都一直不及格，現在好焦慮。你可以教我什麼是牛頓第一運動定律嗎？
```

### 預期輸出

- 助理以基礎、循序方式說明牛頓第一運動定律、慣性與淨力。
- 助理不會宣稱或暗示使用者已理解慣性、已掌握定律，或能力不足。
- 記憶頁不會顯示焦慮、過去成績、能力判定或助理教學內容。

### 後端查核

- 原始訊息可存在於目前對話脈絡，但不得建立 cold candidate 或 verified profile。
- GUM、反思或其他模型流程若產生能力、焦慮或學習成果推論，該輸出只能是短期非 profile working state，且不得走入 cold/profile 寫入路徑。

### 成功標準

回覆具有教學性，但 cold memory 和 verified profile 均不存在焦慮、成績、能力或理解程度的紀錄。

## 第二幕：一次性 SpaceX 查詢與搜尋內容不得形成興趣記憶

### 輸入

在「對話 A」接續輸入：

```text
最新的 SpaceX 星艦發射，有運用到這個定律嗎？請提供資料來源。
```

### 預期輸出

- 若需要最新資料，介面顯示搜尋狀態，回覆包含可辨識的引用來源。
- 回覆可合理連結星艦與牛頓第一運動定律。
- 記憶頁不會顯示長期航太興趣、偏好用星艦學習或已能應用定律等內容。

### 後端查核

- 搜尋結果、引用內容、助理回覆與本次單一問題推導出的 SpaceX 脈絡，不得建立 cold candidate 或 verified profile。

### 成功標準

搜尋與引用正常，但使用者個人資料沒有由單次 SpaceX 問題推導出的興趣、偏好或能力事實。

## 第三幕：偏好問句必須被辨識為查詢

### 輸入

建立「對話 B」，輸入：

```text
我偏好什麼學習方法？
```

### 預期輸出

- 助理可以根據既有 verified profile 回答，或明確表示尚無足夠資訊。
- 記憶頁不會出現此問句或任何由此問句正規化出的偏好。

### 後端查核

- 訊息分類為 `query` 或 `current_focus`，並有不可晉升的原因碼。
- 不建立 preference candidate，不呼叫 profile-memory 寫入。

### 成功標準

含有「我偏好」字樣的問句不會被視為偏好證據，且不會改變長期個人檔案。

## 第四幕：第一次被動明確偏好只能建立 90 天候選記憶

### 輸入

建立「對話 C」，輸入：

```text
我偏好用具體例子理解抽象概念。
```

### 預期輸出

- 助理可使用具體例子回應，但不宣稱已將偏好永久記住。
- 當晉升閾值為 `2` 時，記憶頁不得出現已晉升的長期偏好。

### 後端查核

- 建立一筆 cold candidate，包含原始文字、quoted evidence、`message_id`、`conversation_id`、時間戳記與 user source role。
- candidate 的 `expires_at` 為建立後 90 天；尚未呼叫 `perform_memory_operation` 寫入 profile。

### 成功標準

系統只保存可追溯且有 90 天效期的候選證據；單一對話的一次宣告不會成為 verified profile。

## 第五幕：只有不同對話的重複明確宣告可以晉升偏好

### 輸入

建立「對話 D」，輸入：

```text
學抽象概念時，我希望先看具體案例或實際情境，再理解原理。
```

接著仍在「對話 D」重複輸入：

```text
我真的比較喜歡用實際例子來學抽象概念。
```

### 預期輸出

- 第一則輸入可作為第二個獨立對話的偏好證據。
- 當閾值為 `2` 時，記憶頁可出現語意等同於「偏好用具體例子理解抽象概念」的 verified profile。
- 同一「對話 D」中的第二則重複不得產生第二筆 profile 或增加獨立對話證據數。

### 後端查核

- 晉升證據至少包含「對話 C」與「對話 D」的不同 `conversation_id` 和不同 `message_id`。
- 寫入的 profile memory 使用 `verified_user_evidence`，且只引用使用者原始文字。

### 成功標準

偏好只在兩個獨立對話都有明確宣告後晉升一次；同一對話內重複不會造成重複記憶。

## 第六幕：暫時學習目標有 30 天或完成即移除的生命週期

### 輸入

建立「對話 E」，輸入：

```text
這個月我想完成牛頓運動定律的複習，請在這段期間協助我安排練習。
```

完成後，再輸入：

```text
我已經完成這個月的牛頓運動定律複習目標，請不要再提醒我。
```

### 預期輸出

- 第一則訊息可被系統用於目前的短期學習協助，但不會成為永久 profile。
- 完成宣告後，系統停止以該目標作為提醒或個人化依據。

### 後端查核

- 目標若建立為 cold candidate，必須有 30 天 `expires_at` 或等同的 completion-based removal 規則。
- 完成宣告後，目標標記為完成、過期或刪除，且不能再晉升為 profile。

### 成功標準

暫時目標會在完成時移除，且即使未完成也不會超過 30 天後仍被使用或晉升。

## 第七幕：有效的明確記住指令走獨立的安全晉升路徑

### 輸入

建立「對話 F」，輸入：

```text
請記住：我偏好你先給我一個具體例子，再解釋抽象概念。
```

### 預期輸出

- 助理可確認已處理該低風險偏好，但不應將其他未說明的特徵一併推論為使用者事實。
- 記憶頁可顯示這筆低風險偏好，不需要等待第二個對話作為旁證。

### 後端查核

- 寫入前已驗證 user source role、完整 provenance、低風險分類與非敏感內容。
- profile 寫入有可追溯的 explicit-command 決策與原始使用者引文；不得依賴助理重述或模型推論。

### 成功標準

有效且低風險的「請記住」指令可在單一對話完成安全晉升，但只寫入使用者明確要求的內容。

## 第八幕：記憶頁、更正與刪除必須與實際資料一致

### 輸入

前往記憶頁，檢查第五或第七幕產生的 verified profile。編輯其文字，再重新整理頁面；接著刪除該記憶並再次重新整理。

### 預期輸出

- 頁面只顯示 verified profile，不顯示候選記憶、GUM 命題、學習狀態、搜尋脈絡、scroll 行為、legacy 未驗證資料或 Check/X 核准卡片。
- 編輯後顯示更新文字；刪除後不再顯示，並正常呈現空狀態或其他剩餘 profile。

### 後端查核

- 顯示內容與實際 profile-memory 儲存資料一致。
- 更正或刪除後，相關 profile 必須標示 `STALE`、`REPLACE` 或刪除，且舊 cold candidate、快取或重複晉升不會讓舊值再次出現。

### 成功標準

介面不暴露內部候選流程；編輯、刪除與重新整理的結果完全反映實際資料狀態，舊值不會復活。

## 第九幕：正常 ComPeer 任務必須在時限內完整遞送

### 輸入

在任一測試對話正常閱讀回覆並上下捲動，之後停止操作以觸發 ComPeer。記錄停止操作時間 `T0`，於 `T0 + 120` 秒與 `T0 + 150` 秒檢查信箱與未讀提示。

### 預期輸出

- ComPeer 不會直接插入聊天室，也不會強制開啟角色扮演視窗。
- 約 `T0 + 120` 秒信箱出現新信，未讀數與紅點同步更新。
- 信件內容不會把焦慮、能力推論、單次 SpaceX 問題或未驗證候選說成既定使用者事實。

### 後端查核

- 同一 `task_id` 可依序查到 `scheduled`、`claimed`、`delivered` 事件。
- `mailbox_delayed_tasks` 有對應任務，且信件持久化成功後才更新 `last_compeer_message`。

### 成功標準

信件在約 120 秒送達；至 150 秒未送達即為失敗，且必須有可關聯的 `retryable_failed` 或 `terminal_failed` 原因，而非只有觸發日誌。

## 第十幕：Redis 暫時失敗後，ComPeer 仍可恢復且只送一封

### 輸入

工程人員以另一個乾淨帳號建立可觸發的 ComPeer 狀態，啟用信箱資料庫，並在 delayed-mail enqueue 階段模擬 Redis timeout。執行一次排程器迴圈後恢復 Redis，再執行 delayed-task reconciliation 與 worker。

### 預期輸出

- Redis timeout 當下，使用者不會永久失去此次 ComPeer 遞送機會。
- Redis 恢復後，信箱最終只出現一封對應信件。
- 重複執行排程器與 worker 不會再產生第二封相同信件。

### 後端查核

- `mailbox_delayed_tasks` 先存在可恢復的資料庫任務；原始觸發標記只能在持久化成功後清除，失敗時必須維持或恢復為可重試狀態。
- 相同 `task_id` 最終具有 `scheduled`、`claimed`、`delivered` 軌跡；若仍無法恢復，需有明確重試或終止原因。

### 成功標準

Redis 作為加速佇列失敗時不遺失遞送意圖；資料庫任務可恢復，且使用者可見結果為 exactly-once 的單封信件。

## 最終判定

十幕的成功標準都成立，才可判定本次修正通過人工驗收。任一幕失敗時，記錄幕次、測試帳號、完整輸入或操作、`conversation_id`、`message_id`、`task_id`、`T0` 與實際時間、可見結果及相關後端事件；再回到對應 implementation phase 修正並重跑該幕與相關回歸測試。
