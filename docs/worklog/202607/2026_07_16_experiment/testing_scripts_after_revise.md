# AREQA 修正版人工測試劇本：記憶治理、回覆脈絡與 ComPeer

本劇本驗證 2026/07/16 實驗後的改善項目。測試重點不是只確認記憶頁「看不見」錯誤資料，而是確認未經使用者明確證據支持的內容沒有被寫入長期個人檔案，並且 ComPeer 任務在正常與 Redis 暫時失敗時都具備可追蹤的遞送結果。

## 測試前置條件

- 使用一個全新的測試帳號，且該帳號沒有既有長期記憶、候選記憶或信箱未讀信件。
- 準備三個不同對話：對話 A、對話 B、對話 C；後續新增的對話必須使用新的 conversation ID。
- 記錄 `memory_candidate_auto_promote_conversations` 的實際設定值。以下劇本以閾值為 `2` 說明；若設定較高，應建立相同數量的獨立對話來補足證據。
- 第七、八幕需要工程人員可查詢測試帳號的記憶、`mailbox_delayed_tasks`、信箱資料與結構化日誌。第八幕另需可暫時模擬 Redis enqueue 逾時。

## 第一幕：初次學習問題不得被當成能力或敏感長期記憶

### 輸入

在「對話 A」輸入：

```text
我下週要考高一物理了，但我之前連國中理化都一直不及格，現在好焦慮。你可以教我什麼是牛頓第一運動定律嗎？
```

### 預期輸出

- 助理以基礎、循序的方式說明牛頓第一運動定律、慣性與淨力。
- 助理不會說或暗示「你已經了解慣性」、「你已掌握牛頓第一定律」或等同的結論。
- 重新整理記憶頁後，不出現使用者能力不足、考試焦慮、已理解定律，或助理教學內容等長期記憶。

### 後端查核

- 使用者這則訊息可以存在於目前對話脈絡，但不得被提升為能力、焦慮或學習成果的 profile memory。
- 若 GUM 或反思流程產生能力、焦慮或學習情境命題，該命題不得走入 profile-memory 寫入路徑。

### 成功標準

回覆具有教學性且沒有未經證實的理解判定；記憶頁與後端個人檔案均沒有上述長期記憶。

## 第二幕：一次性 SpaceX 查詢不得形成長期興趣

### 輸入

在「對話 A」接續輸入：

```text
那最新的 SpaceX 星艦發射，有運用到這個定律嗎？請提供資料來源。
```

### 預期輸出

- 若需要最新資料，介面顯示搜尋狀態，回覆包含可辨識的引用來源。
- 回覆可合理連結星艦與牛頓第一運動定律。
- 重新整理記憶頁後，不出現「長期喜歡航太科技」、「偏好用星艦學習」或「已能將定律應用於航太工程」等記憶。

### 後端查核

- 搜尋結果、引用內容、助理回覆，以及由本次單一問題推導出的 SpaceX 脈絡都不得成為 profile memory。

### 成功標準

搜尋與引用正常，但使用者個人檔案沒有任何由單次 SpaceX 問題推導出的興趣、偏好或能力事實。

## 第三幕：偏好問句必須被辨識為查詢，不得建立候選記憶

### 輸入

建立「對話 B」，輸入：

```text
我偏好什麼學習方法？
```

### 預期輸出

- 助理可以根據目前可用資訊回答，或明確表示尚未有足夠證據判斷。
- 記憶頁不會出現「我偏好什麼學習方法？」這個問句，也不會因為此問句出現任何正規化後的偏好記憶。

### 後端查核

- 該訊息應被記錄為 query 或 current-focus 類型，並具備不可晉升的原因碼。
- 不應建立可晉升的 preference candidate，也不得呼叫 profile-memory 寫入。

### 成功標準

問句不會被當成明確偏好證據，且不會改變長期個人檔案。

## 第四幕：第一次明確偏好只能成為具來源的候選證據

### 輸入

建立「對話 C」，輸入：

```text
我偏好用具體例子理解抽象概念。
```

### 預期輸出

- 助理可使用具體例子回應，但不應宣稱該偏好已被永久記住。
- 當閾值為 `2` 時，記憶頁此時不得出現已晉升的長期偏好記憶。

### 後端查核

- 系統建立一筆候選證據，且證據包含原始文字、message ID、conversation ID、時間戳記與 source role 為 user。
- 候選資料尚未觸發 `perform_memory_operation` 的 profile-memory 寫入。

### 成功標準

系統僅保存可追溯的候選證據；單一對話的一次宣告不會直接成為長期記憶。

## 第五幕：只有不同對話中的重複明確宣告可以晉升偏好

### 輸入

建立新的「對話 D」，輸入：

```text
學抽象概念時，我希望先看具體案例或實際情境，再理解原理。
```

接著仍在「對話 D」內重複輸入一次相近句子：

```text
我真的比較喜歡用實際例子來學抽象概念。
```

### 預期輸出

- 第一則輸入可作為第二個獨立對話的明確偏好證據。
- 若閾值為 `2`，記憶頁可出現語意等同於「偏好用具體例子理解抽象概念」的長期記憶。
- 同一個「對話 D」中的第二次重複，不得被計為第三份獨立證據，也不得建立重複的長期記憶。

### 後端查核

- 晉升前的證據集合必須至少包含「對話 C」與「對話 D」兩個不同的 conversation ID，以及不同的 message ID。
- 寫入的長期記憶必須具有 `verified_user_evidence`，且來源只能是使用者原始文字。

### 成功標準

偏好僅在滿足設定的跨對話獨立證據數量後晉升一次；同一對話內的重複陳述不會增加證據數或產生重複記憶。

## 第六幕：記憶頁只呈現長期記憶，且編輯結果與實際資料一致

### 輸入

前往記憶頁，檢查第五幕產生的長期偏好記憶。接著編輯該記憶的文字，再重新整理頁面；最後刪除該記憶並再次重新整理。

### 預期輸出

- 頁面只顯示已驗證的長期記憶與 profile 資訊。
- 不顯示候選記憶、GUM 命題、學習狀態、搜尋脈絡、scroll 行為、舊版未驗證資料或 Check/X 核准卡片。
- 編輯後顯示新文字；刪除後不再顯示，並正常呈現空狀態或其他剩餘長期記憶。

### 後端查核

- 記憶頁資料與實際 profile-memory 儲存內容一致。
- 刪除後不得因舊候選資料、快取或重複晉升而自動重新出現。

### 成功標準

介面沒有暴露內部資料，且編輯、刪除與重新整理後的畫面完全反映實際資料狀態。

## 第七幕：正常 ComPeer 任務必須在時限內完整遞送

### 輸入

在任一測試對話中正常閱讀回覆並進行上下捲動，之後停止操作以觸發 ComPeer。記錄停止操作的時間 `T0`，並在 `T0 + 120` 秒與 `T0 + 150` 秒檢查信箱及未讀提示。

### 預期輸出

- ComPeer 不會直接插入聊天室，也不會強制開啟角色扮演視窗。
- 約 `T0 + 120` 秒時，信箱出現一封新信，未讀數與紅點同步更新。
- 信件內容不會把第一、二幕的焦慮、能力推論或單次 SpaceX 問題寫成既定使用者事實。

### 後端查核

- 同一個 `task_id` 可依序查到 `scheduled`、`claimed`、`delivered` 事件。
- `mailbox_delayed_tasks` 有對應任務，且信件持久化成功後才更新 `last_compeer_message`。

### 成功標準

信件在 120 秒左右送達；若至 150 秒仍未送達，必須明確記為失敗，並有可關聯的 `retryable_failed` 或 `terminal_failed` 原因，而不是只有模糊的觸發日誌。

## 第八幕：Redis 暫時失敗後，ComPeer 任務仍可恢復並且只送一封

### 輸入

由工程人員為另一個乾淨測試帳號建立可觸發的 ComPeer 狀態，啟用信箱資料庫，並使 Redis 在排程 enqueue 階段暫時逾時。執行一次排程器迴圈後恢復 Redis，再執行延遲任務 reconciliation 與 worker。

### 預期輸出

- Redis 逾時當下，使用者不會永久失去這次 ComPeer 機會。
- Redis 恢復後，信箱最終只出現一封對應信件。
- 重新執行排程器與 worker 不會再產生第二封相同信件。

### 後端查核

- Redis 失敗前或失敗時，`mailbox_delayed_tasks` 已存在可恢復的資料庫任務。
- 原始觸發標記僅在持久化任務成功後清除；若持久化失敗，觸發維持或恢復為可重試狀態。
- 相同 `task_id` 最終具有 `scheduled`、`claimed`、`delivered` 軌跡；若恢復失敗則有明確的重試或終止原因。

### 成功標準

Redis 作為加速佇列失敗時不會遺失遞送意圖；資料庫任務可以恢復，且整個流程保持 exactly-once 的使用者可見結果。

## 最終判定

所有八幕的成功標準都成立，才可判定本次修正通過人工驗收。若任一幕失敗，紀錄幕次、測試帳號、conversation ID、message ID、task ID、實際時間、可見結果與後端事件，再回到對應 phase 修正並重跑該幕及相關回歸測試。
