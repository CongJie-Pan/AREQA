### 第三關：後端崩潰重啟與延遲信件韌性 (T1-04)

這是用來確保系統遷移到 Render 後，即便伺服器因休眠或當機而重啟，排定的信件任務也不會遺失。

1. 觸發信件任務：
    • 用您的帳號登入系統，發送一段能觸發背景 Avatar 的對話。
    • 觀察後端終端機，確認出現  [MailboxStore] Added delayed mail task  的日誌（代表信件已存入 Redis 佇列，預設 5 分鐘後送達）。
2. 模擬伺服器斷電：
    • 在信件送達前，直接到終端機按下  Ctrl+C  強制關閉 FastAPI 後端！
3. 等待與重啟恢復：
    • 等待 5 分鐘（確保信件原本的到期時間已過）。
    • 再次執行  uvicorn main:app --host 0.0.0.0 --port 8000  重啟後端。
    • 預期行為：重啟後，背景的 Redis 輪詢 Worker 會立刻發現有「過期未送達」的信件，接著前端畫面上會立刻彈出信件通知 (Mail Alert)！這證明了  asyncio.sleep()  的致命傷已經被 Redis 完美解決。

### 建議補充的測試案例：

#### 1. Cold Memory (Vector 向量庫) 的 RLS 隔離測試 (⚠️ 最關鍵)

目前的第二關測試了  conversations  與  messages  的隔離，但作為 AI 系統，向量資料庫的隔離更為重要。
• 測試目標：確保 User A 的私密對話（被轉化為 Vector Embeddings 存入 PostgreSQL FTS/pgvector）絕對不會在 User B 觸發檢索 (RAG) 時被 Query 出來。
• 測試方法：檢查  cold_memory  相關的資料表（如  document_chunks  或 embeddings 表）是否也有正確設定 RLS Policy。在  authenticated  角色下，用 User B 的 UUID 執行向量相似度搜尋 ( <=>  或  <->
)，確認撈不到 User A 的記憶片段。

#### 2. 離線寫入與斷線重連測試 (Offline Sync)

由於前端使用了 Dexie (IndexedDB) 搭配  syncService ，我們需要確保「本地優先 (Local-first)」機制的強健性。

• 測試目標：模擬網路瞬斷時，用戶仍能操作，且恢復連線後資料不遺失。
• 測試方法：
1. 登入後，關閉網路（或在開發者工具 Network 調整為 Offline）。
2. 在聊天框輸入並發送幾則新訊息（訊息應成功存入 IndexedDB）。
3. 恢復網路連線，觀察  syncService  是否能自動將剛才離線時建立的對話與訊息，正確上傳 (Push) 到 Supabase，且遠端資料庫不發生衝突。


#### 3. WebSocket Ticket 攔截測試 (防禦 CSWSH 攻擊)

針對階段三 (Phase 3) 的架構變更，確保 WebSocket 連線不再暴露於未授權連線。

• 測試目標：驗證 One-Time Ticket 驗證機制的有效性。
• 測試方法：
1. 嘗試使用 Postman 或其他工具，直接對  ws://localhost:8000/ws  發起連線（不帶 Ticket）。
2. 預期行為：後端應立刻拒絕連線 (HTTP 403 或是中斷連線)。
3. 取得合法的 Ticket 後連線，但在 10 秒後使用「同一個 Ticket」進行第二次連線。
4. 預期行為：因為 Ticket 是用過即焚 (Redis  GETDEL )，第二次連線應被拒絕。


#### 4. Redis Hot Memory 快取淘汰與轉移測試

系統設計了 Hot Memory (近期記憶) 與 Cold Memory (長期記憶)。

• 測試目標：確保短期的 Redis 資料能正確過期，並無縫依賴 PostgreSQL 的長期記憶。
• 測試方法：
1. 大量寫入訊息，超過 100 則（或是強制修改 Redis 中該 User 的 key TTL 讓其過期）。
2. 再次與 AI 對話，詢問稍早前提及的特定關鍵字。
3. 預期行為：AI 依然能精準回答，且後端 Log 應顯示系統成功觸發了  query_cold_memory_for_context  (Cold Memory 檢索)，而不是依賴 Redis，證明冷熱記憶交接順暢。
