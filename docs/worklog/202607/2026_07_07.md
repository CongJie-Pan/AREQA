繼續資料庫人工驗證工作 :

### 如何進行 Phase 1 ~ 3.5 的「人工測試確認」(Manual Verification) ?

你提到的：「我要如何確認計畫書的人工測試通過？(進行phase 1 - 3.5的人工確認?)」，你可以依照以下步驟來進行端到端的完整測試，確認你最在意的「不管在用哪個裝置登入網頁，都會同步我的資料包括對話紀錄」：

#### 步驟 1：啟動完整環境

打開終端機，執行專案的啟動指令：

npm run build
npm run start

確保 FastAPI (Backend) 與 Next.js (Frontend) 皆正常啟動。

### 第一關：多帳號隔離與跨裝置同步測試 (T3-04, T3.5-01, T3.5-02)
這是最重要的前端實機體驗，確認多租戶機制是否真的發揮作用。

1. 基本登入與資料寫入：
    • 在瀏覽器點擊左下角的 Auth UI 進行登入（可隨意註冊一個信箱  userA@test.com ）。
    • 進入畫面後，新建一個對話，並傳送幾則訊息（例如：「這是 User A 的秘密對話」）。
2. 登出與本地資料抹除測試：
    • 點擊左下角進行「登出 (Logout)」。
    • 預期行為：畫面應立刻退回登入前狀態，若打開瀏覽器開發者工具 (F12) -> Application -> IndexedDB，裡面的對話紀錄應該已被完全清空。
3. 換帳號隔離測試：
    • 使用另一個帳號  userB@test.com  註冊/登入。
    • 預期行為：畫面上應該是一片空白，絕對不能看到剛才 User A 的「秘密對話」。
4. 跨裝置 (跨瀏覽器) 雲端拉回測試：
    • 請打開瀏覽器的「無痕模式 (Incognito)」（模擬換了一台新電腦）。
    • 在無痕模式中，登入回剛才的第一個帳號  userA@test.com 。
    • 預期行為：登入完成的瞬間，系統應會觸發  syncService ，將 User A 先前的歷史對話從 Supabase 完整拉回並顯示在畫面上！


### 第二關：Supabase RLS 資料庫層級防護 (T2-04)

這項測試用來確保即使後端被駭或是有人直連資料庫，也無法偷看其他租戶的資料。

1. 進入 Supabase 儀表板：
    • 前往您的 Supabase 專案 -> 左側點擊 SQL Editor。
2. 執行越權查詢：
    • 在 SQL Editor 貼上並執行： SELECT * FROM conversations;  或  SELECT * FROM messages; 。
    • 預期行為：執行結果必須是 0 行資料 (No rows returned)，因為 SQL Editor 預設沒有帶入  auth.uid() ，PostgreSQL 的 RLS 政策會將所有資料隱形。
3. （選做）模擬合法查詢：
    • 若您想證明資料還在，可以手動注入角色：

-- 替換為您的測試帳號 UUID
set request.jwt.claims to '{"role":"authenticated", "sub":"您的-USER-UUID-貼在這"}';
SELECT * FROM conversations;

    • 預期行為：這時就能正常查出該名 User 剛剛寫入的紀錄。


### 第三關：後端崩潰重啟與延遲信件韌性 (T1-04)

這是用來確保系統遷移到 Render 後，即便伺服器因休眠或當機而重啟，排定的信件任務也不會遺失。

1. 觸發信件任務：
    • 用您的帳號登入系統，發送一段能觸發背景 Avatar 的對話。
    • 觀察後端終端機，確認出現  [MailboxStore] Added delayed mail task  的日誌（代表信件已存入 Redis 佇列，預設 5 分鐘後送達）。
2. 模擬伺服器斷電：
    • 在信件送達前，直接到終端機按下  Ctrl+C  強制關閉 FastAPI 後端！
3. 等待與重啟恢復：
    • 等待 5 分鐘（確保信件原本的到期時間已過）。
    • 再次執行  uvicorn main:app --host 0.0.0.0 --port 8000  重啟後端。
    • 預期行為：重啟後，背景的 Redis 輪詢 Worker 會立刻發現有「過期未送達」的信件，接著前端畫面上會立刻彈出信件通知 (Mail Alert)！這證明了  asyncio.sleep()  的致命傷已經被 Redis 完美解決。
