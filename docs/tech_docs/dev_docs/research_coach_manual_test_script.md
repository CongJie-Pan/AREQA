# Topic Finder（選題）實機測試劇本

- 對應計畫：`docs/tech_docs/dev_docs/research_coach_planning_and_task.md`（第 6.6 節）
- 劇本來源：`docs/user_experience/chat_record/areqa-chat-2026-11-07.pdf`
  - 一位準備國外國關碩士申請的同學，在一般模式下用 AREQA 找研究題目的完整紀錄：119 頁，學生發言 56 次。
  - 本劇本直接用他的原文當輸入（見附錄），逐步對照「原本 AREQA 怎麼回」與「選題應該怎麼回」。
- 用途：自動化測試全部通過後，由作者在真實環境（真實後端、Supabase 與模型）中手動驗收。
- 填寫方式：每一步在「結果」欄填 ✅／❌，有狀況寫在備註；最後填「評分表」並簽核。

## 為什麼用這份紀錄

這份紀錄正好是選題空間要解決的問題。原本 AREQA 的表現：

| 指標 | 原本 AREQA |
|---|---|
| 題目方向更換次數 | 9 次：韓國對中政策 → 台灣公民外交 → 文化與國關理論 → 歐洲穆斯林移民的安全化 → 法國個案 → 回到韓國（新古典現實主義）→ 文化建構主義 → 新古典現實主義 → 韓國半導體的戰略自主 |
| 回覆開頭先稱讚（「極具學術價值」「展現非常紮實的問題意識」等） | 50 次回覆中 17 次 |
| 每則回覆平均長度 | 約 2,000 字 |
| 每則回覆平均提問數 | 2.2 個 |
| 換題時提醒「這和先前的題目有什麼關係」 | 幾乎沒有，大多順著新題目繼續延伸 |
| 最後一句（U51）連續送出 6 次 | **一次都沒有回覆** |

選題空間預期的改變：
- 換題時要指出「這是換題」，並問原因，舊題目記進淘汰清單（可以降級保留）。
- 選擇點先提反對理由，不先稱讚。
- 不替學生寫好完整的題目或研究計畫。
- 不替學生宣告過關。

## 0. 事前準備

1. **套用 Supabase migration**（Supabase SQL Editor 或 `supabase db push`），依序執行：
   - `supabase/migrations/20261118000000_conversation_kind.sql`
   - `supabase/migrations/20261118010000_research_topic_cards.sql`
   - 確認：`conversations` 有 `kind` 欄位（預設 `chat`）；`research_topic_cards` 已開啟 RLS，且瀏覽器角色沒有權限。
2. **確認後端環境變數**：`DATABASE_URL`（題目卡寫入用）、`OPENROUTER_API_KEY`。
3. **確認部署版本**：前端已包含 commit `939fbca` 之後的版本（`/api/chat` 會轉送 `conversation_kind`）。驗證方式：在選題對話送出一則訊息後，後端日誌的 `stream.request_accepted` 要出現 `conversation_kind=research_coach`。
4. **啟動服務**（在專案根目錄）：
   - 一次啟動前後端：`npm run dev`
   - 或分開啟動：
     - `./backend/.venv/bin/python -m uvicorn main:app --app-dir backend --host 0.0.0.0 --port 8000 --reload`
     - `npm run dev --prefix frontend`
5. **準備兩個帳號**：
   - 帳號 A：已經有舊對話（在這次功能之前建立，沒有 `kind`），而且**從沒進過選題**。
   - 帳號 B：新帳號，用來測試使用者之間互相看不到題目卡。
6. 介面語言設為繁體中文（劇本 G 才切換語言）。
7. 劇本 B 的輸入都在附錄。**請完整貼上原文，不要改寫**，才能和原本 AREQA 的回覆對照。

## 劇本 B｜主線：國關碩士申請者找題目

**操作方式：**
- 在選題空間開一則新對話，依序貼上附錄的原文。
- 標「（自擬）」的是本劇本新增的回應：原文是在回應舊版 AI 的選項，接到新教練會對不起來，所以改寫成同樣意思、但不依賴舊回覆的句子。
- 每一步都看三件事：AI 的回應、右上角的階段標籤、右側題目卡。題目卡的更新在回答完成後約 3～9 秒出現。
- 表中的「確認」是指按題目卡的「對，就這樣，進入下一關」（沒有 AI 草稿時是「這一關我想清楚了，進入下一關」）。
